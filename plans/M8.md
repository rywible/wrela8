# M8 plan: multicore

**Status: ACTIVE.**

First deliverable of the milestone, per the planning convention. The docs
carry the substance — [02-language.md](../docs/language/02-language.md)
§9 (placement, mailboxes, admission), [04-compiler.md](../docs/language/04-compiler.md)
§2 / §7 (whole-image analyses must show causality),
[06-machine.md](../docs/language/06-machine.md) §1 (vCPU count) / §4
(checkpoint injection) / §5 (doorbells) / §8 (record/replay; the

"Placement inference, cross-core rings, **3 vCPUs**, per-mailbox
admission recording. Flips: `actors.placement.deterministic`."

The machine is **3 vCPUs, always** — settled in ROADMAP (2026-07-24):
`vCPUs = flagship core count − 1 housekeeping core` (Pi 5: 4 − 1 = 3).
That number change is a golden-moving, deliberately reviewed commit of
its own (06 §1, README, `wrela-machine` stack-region docs, and every
report layout that enumerates `core_stack_N`).

## Goal

An image places actors across three cores, cross-core sends travel on
declared rings, and every mailbox's admission order is a recorded choice
the replay path can inject. Placement is a build output the report
states and the recorder's choice sequence enumerates — not a runtime
heuristic. The M6/M7 single-core surface keeps working; core 0 remains
the home of the virtio-blk driver and its bottom half until a later
item moves one deliberately.

## The honest scope line (decide once)

IN: the 4→3 vCPU layout edit and its golden move; placement inference
that assigns every `@actor`/`@driver` a core (fail closed when it
cannot); cross-core rings sized and placed from the sealed graph;
`ChoiceEntry::Admission` becoming a real recorded tag (M6 shipped the

lifting the M7 floors that multicore or messageable drivers force

that would own it): a fourth vCPU; a second device family (display/input
or any other 06 §6 contract — no rung of the ladder owns one);
`Validated[F, T]` / `Secret[T]` as full marked policies (M7 H2a left
them out of the honest-scope line —
`values.marked.mechanism` already rejects them by name; lifting is
stdlib-era, not a multicore deliverable); cost-model work
(`compiler.costs.predicted-vs-measured` — M11); runtime-in-wrela (M10);
hybrid IRQ/poll *policy* libraries; IOMMU mapping; schedule exploration
/ partial-order reduction (still the coverage pass; fail closed over
budget).

  every golden that enumerates cores; a placement dump / report section

  exercises a cross-core send and a recorded admission choice; every
  existing single-core lane still clean.

- `ChoiceEntry::Admission` is no longer format-only: record → replay
  clean → tamper an admission choice → divergence, on a named workload

- Deep fuzz all live lanes, 3+ fresh seeds, clean.
- The M7 carry-forward floors below are each either flipped or recorded
  as an explicit gap with the owning item named — not silently absent.
- `plans/M9.md` does not exist yet.

## Shape decisions (frozen by goldens — decide once)

1. **Three vCPUs is a machine-revision constant, not a knob.** ROADMAP
   already settled the derivation. Item A is the golden-moving commit
   that makes the number true in artifacts; no runtime "how many cores"
   discovery (06 §3).
2. **Placement is a build output.** The report names each actor's core;
   source may annotate `core=N` where inference is too weak, and omitted
   annotations are inferred or rejected — never silently defaulted to 0
   for a cross-core graph. The virtio-blk driver and its ISR/bottom half
   stay on core 0 unless an item deliberately moves them with an oracle.
3. **Admission joins the choice sequence for real.** M6's
   `ChoiceEntry::Admission` tag stops being format-only. Cross-core
   admission order is the nondeterminism ROADMAP named beside device
   completion timing; both are injectable. The recorder's representation
   stays an enumerable choice sequence (no opaque timestamps).
4. **One driver-fault story until quarantine lands.** M6 decision 12 /
   M7 decision 8: an actor/driver abandon is image-fatal with a
   diagnosable line. Quarantine and recovery turns are an ordered item
   of this milestone (below), not a silent change to that floor.
5. **Driver mailboxes lift before caller-side `await receipt` executes.**
   M7 decision 22 left `await receipt` typed and lowered but unreachable
   from the flagship because `@driver` mailboxes stay the M6-D floor
   (`golden/err-image-driver-message`). The mechanism is shared with
   sync `claim`; what is missing is the messageable-driver API in
   `05-library.md`. Item order below puts that API before any oracle
   that needs a parked caller-owned receipt.

## Decisions recorded (item B)

### Decision 6 — single-core floor until a cross-core annotation exists

04 §3's packing algorithm assigns each unfixed actor to the core whose
resulting `(work, bytes)` load is lexicographically smallest. With
`work=0` for everyone (decision 7) that spreads actors across cores 0/1/2
by bytes alone. Secondary vCPUs are not started until item C, so
spreading unannotated actors would silently strand them and break every
M6/M7 boot.

**Rule:** when no declaration carries an explicit `core=` ≥ 1, the live
assignment domain is `{0}` — every unfixed placeable lands on core 0.
When any `core=` ≥ 1 is present, the graph is cross-core and the full
`VCPUS`-wide packing runs for the unfixed rest (report oracles at B;
multicore boot at C).

**Rejected:** always pack across three cores and hope boots only use
actors that happen to land on 0 — fail-open. **Rejected:** require
`core=0` on every existing image — golden-moving ceremony for a floor
the plan already promised to keep working. **Rejected:** invent a
"soft" placement in the report and a different "hard" one for
execution — two truths.

### Decision 7 — unproved turn work is published as 0, not invented

04 §3 sorts on proved maximum uninterrupted turn work. The cost model
that would prove it is honest-scope OUT (M11). Using equal `work=0`
with `work_source=unproved` in every Placement line keeps the algorithm
total and the report honest; relative rankings come only from bytes and
identity until M11.

**Rejected:** fail closed every image that omits `core=` because work is
unproved — would force annotations on the entire corpus for no new
fact. **Rejected:** invent synthetic work from method counts / IR size —
not a published proof.

### Decision 8 — virtio-blk pin is by bound device type `VirtioBlock`

Shape decision 2: the virtio-blk driver and its ISR/bottom half stay on
core 0. The pin keys off the driver's bound device type being named
`VirtioBlock` (the machine's one block device), not the driver struct
spelling (`BlkDriver` / `BlkDriver[DriverMode.Irq]` / a test alias).
`core≠0` on such a driver fails closed by name.
`BlockHw`-bound test drivers are ordinary placeables (inferred / explicit).

**Rejected:** pin every `@driver` — over-broad; the plan named virtio-blk.
**Rejected:** pin by struct name substring `Blk` — fragile against
renames and false positives.

### Decision 9 — 02-language.md §9.1 "four cores" → "three cores"

Item A updated 06 / 01 / 04 / README / `VCPUS` but left 02 §9.1 saying
"four cores". Normative docs must agree; fixed in the same item that
makes core assignment real. No behavior change beyond the wording.

## Decisions recorded (item C split)

### Decision 10 — item C is three items, not one

Item C as written bundles three independent machines: making a second
and third vCPU execute at all (today `boot_image_core` creates exactly
one `hv_vcpu`), lowering cross-core edges to 04 §3's bounded SPSC rings,
and turning M6's format-only `ChoiceEntry::Admission` into a recorded
choice with a tamper oracle. Each has its own failure mode and its own
oracle; bundled, a green gate would not say which of the three is real.
They land in the order C1 → C2 → C3, each a commit with its own goldens.

`actors.placement.deterministic` flips at **C2**, not C1: placement is
only load-bearing once a message actually has to cross a core boundary
to be delivered. C1's evidence is that three cores run and every
existing transcript is unchanged; that is a floor, not the clause.

**Rejected:** flip the clause at C1 on the strength of the report's
Placement section alone — item B already publishes that table, and a
clause that a boot cannot falsify is not tested. **Rejected:** do C3
first because it touches only the recorder — cross-core admission order
is the thing being recorded, and with one core there is no cross-core
admission to observe; the entry would stay synthetic.

### Decision 11 — three vCPUs execute, but never concurrently

04 §2 makes cross-core admission order at each mailbox the machine's
*only* scheduling nondeterminism, and 06 §8 requires the recorder's
representation to stay an enumerable choice sequence. Three host threads
each in `hv_vcpu_run` at the same time would make interleaving — not
just admission order — nondeterministic, and `xtask repro` would be
measuring the host's scheduler.

**Rule:** Hypervisor.framework requires a vCPU to be created and run on
the thread that created it, so there are three host threads; a single
baton passed between them means exactly one vCPU is inside `hv_vcpu_run`
at any instant. The baton hand-off order is a deterministic function of
guest-visible state (pending words and the run queue), never of host
timing. Every existing single-core recording must replay unchanged, and
`xtask repro` stays green — that is C1's acceptance test, not a nicety.

**Rejected:** run the three vCPUs truly concurrently and log enough to
replay — the log would be an opaque interleaving trace, which 06 §8
forbids by name. **Rejected:** emulate secondary cores by round-robining
one vCPU's register state — three cores that are one core is a second
truth the report already contradicts. The cost is that the flagship's
multicore boot is not *faster*; M8 buys placement and cross-core
semantics, not throughput. That trade is accepted, as M10's is.

## Decisions recorded (item C1)

### Decision 12 — the bring-up set is the placement domain, and a single-core image emits nothing

Item B's decision 6 already made the *packing* domain `{0}` unless some
declaration names `core=` ≥ 1. C1 reuses that one predicate as the
**bring-up** set: a single-core image emits no secondary entry blocks, no
`CoreEntry` report lines, no release store, and no per-core scheduler
stripes beyond core 0's. That is not an optimization — it is what makes
"every existing single-core boot transcript is byte-identical" true *by
construction* rather than by measurement, and the golden set proves it
(exactly one file moved, `check-placement-cross`, the only pre-existing
cross-core golden).

**Rejected:** bring up all three cores on every image, so the machine is
uniform. It would move every layout-carrying report golden, add two vCPU
creations and two entry blocks to every image including `boot-hello`, and
buy nothing an empty loop that immediately parks does not already do. The
mandate's "a core with no actor placed on it must come up, find nothing,
and park" is honored where it is observable — inside a cross-core image,
core 2 has no actor placed on it and still comes up, marks itself, finds
nothing and parks (`golden/boot-cross-core`). **Rejected:** a runtime "how
many cores" probe (06 §3 forbids discovery outright).

### Decision 13 — the release is a guest action on a trapping doorbell, and the baton moves only on guest actions

06 §3 assigns the release to the *entry*, not to the VMM: "the entry
installs per-core state, releases the other vCPUs, runs typed driver and
actor initialization ... and enters the per-core event loops." So the guest
rings `mmio::RELEASE_MMIO_ADDR` with the core count it brings up, and the
VMM refuses any other value, a release from a core other than 0, a second
release, and a report whose `CoreEntry` set disagrees. The baton then
changes hands at exactly two guest actions — that release, and a park —
and at no other exit.

That last clause is the load-bearing one. Handing off at *every* exit would
interleave cores at clock reads and device completions, making the schedule
depend on how often the guest happens to trap; handing off only when the
guest volunteers keeps the hand-off sequence a function of the program.
Boot init still runs before any turn anywhere, because a released core is
*eligible* for the baton, not running on it, and every secondary parks on
its first pass (its mailboxes are provably empty until item C2).

**Rejected:** start the secondary vCPUs from the VMM at boot, before core 0
runs — simpler host-side, and a direct contradiction of the chapter
sentence, with the secondaries scanning tables core 0 has not initialized.
**Rejected:** a shared-memory release word polled by the VMM — a poll needs
a polling site, and the only ones are vCPU exits, so it degenerates to the
trapping store with a delay. **Rejected:** an `MPIDR_EL1` read so one entry
block serves all cores — `msr`/`mrs` is M10 floor territory, `encode.rs`
has no such encoding today, and per-core entry addresses are a build output
the report already knows how to publish.

### Decision 14 — a secondary core's park is terminal until a wake exists

A secondary core with nothing ready performs the ordinary park store; the
VMM deschedules it until its own pending word is nonzero. It does **not**
consult `machine_info::OFF_NEXT_DEADLINE` (one word, the boot core's), does
not sleep on a host clock, does not spin, and does not call
`__wrela_checkpoint_service` on resume. At C1 nothing can raise a
secondary's pending word, so in practice it parks once and stays parked —
which is precisely the floor C1 promises, and the VMM fails closed if
*every* core reaches that state (`core N parked and no core is runnable`)
rather than hanging.

**Rejected:** per-core deadline words now — no turn can run on a secondary
core, so no deadline can be armed there; adding three words and a per-core
park protocol would be building C2's wake path on speculation. **Rejected:**
have a parked secondary poll its own pending word between `hv_vcpu_run`s —
that is the busy-wait the mandate forbids by name.

### Decision 15 — a cross-core message edge is a build error until C2

Codegen lowers `send`/`await` through an `Actor[X]` handle to the same-core
`__rt_enqueue_X` admission routine. With per-core loops that call, made
across a core boundary, writes a mailbox whose owning core will never be

## Decisions recorded (item G)

### Decision 17 — the outcome rides `VirtQueue.recover`, not `IoCompletion`

M7 decision 24 offered two flip routes for condition (a): put a
`CompletionOutcome` discriminant on `IoCompletion`, **or** on the receipt
resolve path. Chose the second, and the reason is a safety property, not a
taste:

`claim(receipt=take r) -> IoCompletion[P]` returns the payload —
03 §3 says so normatively and shows it (`buffer = take completion.payload`,
"ownership returns with the completion"). That is sound only because the
device provably returned the descriptor under the live epoch. The one
honest `Unknown` producer is the opposite case: an operation in flight
across a reset, where 03 §9 says "After a reset, a write may have happened"
and, one sentence later, "it never reclaims possibly device-owned memory".
An `IoCompletion` carrying `outcome=Unknown` would have to hand the buffer
back anyway — turning today's fail-closed abort into a survivable path that
returns memory the device may still write. That is a safety **regression**
bought to flip a clause.

**Chose:** `queue.recover(receipt=take r) -> CompletionOutcome` — 03 §5's
`Recovery` state, which the receipt state machine already names, and the
path §9 describes for cancelling in-flight work ("a driver protocol, not a
dropped future"). It consumes the receipt (resolves-exactly-once holds),
reports the outcome, and returns **no payload**. `claim` is untouched and
remains the resolved path. Two states of one machine, not two ways to do
one thing.

Outcome derivation (`virtqueue::recover_outcome`, one pure function
`codegen::emit_queue_recover` emits ladder for ladder): stale epoch →
`Unknown`; still `INFLIGHT` → `Unknown`; `RESOLVED` under the live epoch →
the virtio-blk status byte decides `Completed` / `NotCompleted`; anything
else is a named driver-fault abort. The epoch test is **first**, mirroring
`validate_completion_id`'s own ordering, so a receipt a reset invalidated
reports `Unknown` even when the pre-reset drain had already resolved it —
which is exactly what the flagship stages.

`CompletionOutcome` is a prelude enum carrying 03 §9's three variants in the
doc's declaration order. Making it matchable required one general
improvement rather than a special case: `matches::shape_of` and
`bodies::variant_payload_types_for` now read *any* prelude enum's variants
out of `builtin_enum_variants`, so `Target`/`Restart`/`BootError`/`IoError`/
`DriverMode` became matchable in the same commit.

**Rejected:** `IoCompletion[P].payload: Option[P]`, so an `Unknown`
completion could carry no payload. It works and the type would carry the
fact — but it contradicts 03 §3's normative prose *and* its worked example,
so it is a normative doc change, and it moves every existing driver. A doc
edit is the expensive kind of change here and this rule needed none.
**Rejected:** returning the payload on `Unknown` and recording quarantine as
a gap — that is building the hole, and it makes the machine less safe than
before the commit. **Rejected:** an `IoCompletion.outcome` field *plus*
`recover` — `Completed`/`NotCompleted` would gain a second producer for no
new fact, at the cost of moving the completion stash and every layout
golden. **Rejected:** flipping on `recover` alone with `Completed`/
`NotCompleted` unproduced — that is precisely M7's own refusal ("inventing a
`CompletionOutcome` enum with no producer to flip a clause"), which is why
`recover` classifies all three rather than always answering `Unknown`.

### Decision 18 — non-idempotence is declared at `prepare_block` and carried by `QueueOp`'s type

The compiler cannot infer non-idempotence: a fixed-bytes write to a fixed
sector is idempotent, an append is not, and both spell the same
`prepare_block`. Inventing an inference is exactly the cleverness ROADMAP
forbids, and it would be *unsound* in the direction that matters.

**Chose:** a **required** `idempotent=` argument on `prepare_block`, whose
value must be the literal `true` or `false`, and which becomes a second type
argument on the operation: `QueueOp[P, <idempotent>]`. Required rather than
defaulted, because a default in either direction is the compiler guessing on
the author's behalf about a fact only the author knows. Carried by the type
rather than by the call site, because the rejection has to fire at `publish`
too — otherwise hoisting the `prepare_block` out of the arm launders the
retry.

The rule: inside a `match` arm that can match `CompletionOutcome.Unknown`,
neither `prepare_block(..., idempotent=false)` nor `publish` of a
`QueueOp[_, false]` is legal. "Can match" is deliberately
over-approximate — a wildcard or a plain binding covers `Unknown` as surely
as naming it does, and the fail-open reading of this rule is the one that
lets a write land twice.

**Note on the docs.** 03 §4's worked `prepare_block` line already ends in
`...`, so a new labelled argument contradicts nothing normative and this
item ships with **no `docs/language/` edit** — §9 already states the rule
being enforced. No REVIEW-QUEUE line is owed.

**Rejected:** a `@non_idempotent` attribute on the issuing `fn`. It is a new
normative language surface (a doc change plus a clause) for a fact that
belongs to the *operation*, which is what §9 talks about. **Rejected:**
optional `idempotent=` defaulting to `false` (fail-closed but silent: the
author never states the thing the rule is about, and every existing driver
would silently become non-idempotent). **Rejected:** defaulting to `true` —
fail-open, immediately. **Rejected:** inferring it from
`device_writes_payload=` or from the blk request type — an inference, and a
wrong one (a read is idempotent, but so is a fixed-sector write). **Rejected:**
a runtime poison bit in the slot book (queue marked "outcome unknown";
`publish` of a non-idempotent op aborts). Airtight against the helper-call
laundering the lexical rule misses, but §9 says "**Source** must not
auto-retry", which is a source rule, and it would move `SLOT_BOOK_BYTES` and
every blk pool size in every report golden. Admissible later on evidence;
the laundering hole is recorded as thin rather than papered over.

### Decision 16 — the regions clause does not flip; its condition does

### Decision 19 — a messageable driver is a mailbox root, not a driver-shaped copy of one

05-library.md §9 already spells `img.driver(A[...], device=d, ...)` and
`img.actor(A, mailbox=n, ...)` as one family of "actor declarations", and
02 §9.1 already says a `@driver` **is** an actor. So messageability is a
declaration label, not a new construct: `img.driver(D, mailbox=n)` gives
`D` a mailbox, and everything downstream treats it as one more *mailbox
root* in a single ordered list (`layout::mailbox_root_names` — every
declared actor, then every messageable driver).

**Rule:** one loop in `build_runtime_glue_block` emits every root's
`rt_enqueue_*` / `rt_select_and_run_*` pair by calling the *identical*
`build_rt_enqueue` and `build_rt_select_and_run_symbolic` an actor uses;
one `place_runtime_tables` loop lays out the same five regions in the same
order; one `merge_actor_pub_methods` supplies both dispatch tables; one
`rt_run_one` round robin selects both. Nothing below admission can tell an
actor from a driver. The plan's "does not invent a second completion path"
is therefore structural rather than a promise: there is no second path to
invent, because there is no driver-specific routine at all.

**Rejected:** giving `DriverRuntimeLayout` its own admission/dispatch
assembly — two copies of the hardest hand-written code in the compiler,
which is exactly the shape M10 exists to delete. **Rejected:** moving a
messageable driver's entry into `RuntimeTables::actors` and dropping its
`DriverRuntimeLayout` — the driver row carries state size, the
wake-pending offset and the ISR table's base address, and every M7
consumer indexes `graph.drivers`; re-keying them to buy one shared `Vec`
would move goldens for no new fact. **Rejected:** making every `@driver`
messageable and deriving the capacity — 04 §2's derivation from the closed
sender set is real work nobody has done, and M6 decision 3 already settled
that the declared bound is the whole capacity story. Opt-in also keeps
every existing golden byte-identical, which is the evidence that the lift
added a surface rather than changing one.

### Decision 20 — the authority rule stays in sema; only the receipt floor is new

03-hardware.md §1's "a driver may export safe actor APIs but never raw
capabilities" is already enforced by
`sema::types::validate_fn_capability_types` for every `pub` method of an
`@actor`/`@driver`, messageable or not (M7 decision 3: "Capabilities are
checked where `Actor[T]` already is ... do not build a second mechanism").
Item D does **not** re-implement it against the image graph.

What item D found and fixed there is one hole that only opens once a driver
can be messaged: `QueuePermit` / `QueueOp` were whitelisted **ahead of**
the pub-method rejection, so a `pub` driver method could declare a sealed
queue value as its reply. Harmless while nothing could call it; a
laundering channel the moment something can. They now fall through on an
exported reply (`is_pub_method && owner != Plain`) and stay permitted
everywhere 03 §4 actually needs them — a private driver method and a free
helper.

`Receipt[P]` keeps its whitelist, because 03 §5 blesses that public driver
signature by name. That is exactly the handoff convention item E owns, so
a *messageable* driver declaring one is refused at the image with a
diagnostic naming item E (`layout::check_driver_message_surface`). That
one refusal is the only authority arm item D adds, and it exists because
it is a floor with an owner, not a rule.

**Rejected:** re-checking every parameter and reply for sealed authority in
layout as defence in depth — sema runs first and refuses all of them, so
every such arm would be dead code, and this file's own precedent
(`type_contains_capability`'s "captures" note) is that an unreachable arm
is named rather than written. **Rejected:** deleting the `Receipt`
whitelist outright to close the hole "properly" — it would refuse
`golden/check-receipt-handoff`, which is 03 §5's own worked shape on a
non-messageable driver and is legal today.

### Decision 21 — a driver mailbox admits `pub` methods only, and a `@task`/ISR may not be `pub`

03 §6 gives a driver two *other* entry paths: an ISR bound with
`irq.bind`, and a `@task` bottom half entered by `wake`. Both run against
live device state under §6's own ordering. Admitting either from a mailbox
would run device work as an ordinary turn, at an arbitrary time, on behalf
of an arbitrary sender — and, for the bottom half, would give one turn body
two entry paths with only one of them ordered against the interrupt.

**Rule:** on a driver declared with `mailbox=`, a `pub` method that is
`@task` or is an `irq.bind` target is a build error naming which of the two
it is. Private ones are untouched — `boot-driver-message` boots an ISR *and*
a `@task` *and* a mailbox on one driver, which is the evidence that the
rule is a boundary and not a restriction.

**Rejected:** making it unconditional at sema ("a `@task` may never be
`pub`"). It would be a new normative rule for a hazard that does not exist
without a mailbox, on every driver in the corpus, decided by an item that
was not asked to decide it. **Rejected:** silently excluding `@task`/ISR
methods from the dispatch table — a `pub` method that is not callable
through `Actor[T]` would contradict 05 §2 ("exposes only `T`'s public actor
methods") and would be invisible in the report.

### Decision 22 — an `Actor[T]` runtime-test parameter may name a messageable driver

`layout::resolve_runtime_test_args` refused a driver handle by name,
citing the same M6-D floor. It resolves one now when the driver carries
`mailbox=`, and keeps a named refusal (pointing at the label) when it does
not. Nothing reads a handle word at runtime — codegen routes every
`await`/`send` statically by actor type — so the index is the same
build-time identity the report already prints as `driver#0`.

**Rejected:** leaving the test-arg floor and routing every test through a
relaying `@actor`. The relay is worth having and `boot-driver-message` has
one, but it cannot distinguish "the driver ran a turn" from "the relaying
actor ran a turn and guessed"; a root that awaits the driver directly can.

### Decision 23 — `InterruptCell[T]` may not cross a driver mailbox, in either direction

Found by the orchestrator's capability-escape sweep against
`boot-driver-message`'s own driver, after the first item-D commit: seven
probes, six refused, `pub fn leak_cell(read self) -> InterruptCell[u32]`
**accepted** — and an ordinary `@actor` could `await` it, bind the `Ok`
arm, and store the result in its own `InterruptCell[u32]` field, whole
program type-checking clean. Re-probing the parameter direction found the
same hole there.

The reason it slipped every existing rule is a decision that is still
right: M7 decision 17 settled that `InterruptCell` is a builtin like
`Actor[T]` and **not** a capability — `InterruptCell(v)` is
source-constructible, an `@actor` may hold one, and each of the structural
rules the sealed-authority list drives (unforgeability, `@layout`
exclusion, protocol consumption, actor containment) would give the wrong
answer for it. So `contains_capability` does not range over it, and neither
did item D's message-shape check, which was built on that same predicate.

What is true of it is narrower and belongs precisely at this boundary. 03
§6: "`InterruptCell[T]` is the **sole** ISR/ordinary-code channel ...
interrupt-atomic with respect to every vector that may touch the cell." A
mailbox is a different channel between different principals; a cell that
crosses it is a second, unordered one, handing the interrupt-status word's
value to a sender that owns none of §6's ordering.

**Rule:** on a driver declared with `mailbox=`, a `pub` method whose
parameters or reply carry an `InterruptCell` at any nesting is a build
error quoting §6's "sole". Implemented by making the *leaf set* a parameter
of the one existing walk (`sema::types::type_carries_named`), not by adding
a second walk: containment asks it about sealed authority, the driver
message shape asks it about sealed authority **plus** `InterruptCell`, and
both inherit the same `Option`/wrapper-struct/cycle-guard reach — the
absence of which is exactly the class of miss item I's sweep found once
before (`golden/err-dma-shared-lend-wrapped`).

This required widening 05-library.md §2's own sentence (". . . no
capability, sealed queue value, protocol state, **receipt, or interrupt
cell** crosses a driver mailbox"), because otherwise the compiler would be
enforcing a rule the normative text does not state. Second REVIEW-QUEUE
line, same clause.

**Severity, honestly.** Latent, not live. The cell's four operations lower
to `InterruptCell*` instructions against `self.<field>` with a `field_off`,
so calling one on a *received* value stops at `error[unimplemented]:
mirroring a method call through this base expression is not checked yet`,
and the cell is copied by value so the receiver's does not alias the
driver's. Pinned anyway: the value itself already crossed, and the aliasing
half becomes live the day method calls through arbitrary base expressions
land.

**Rejected:** adding `InterruptCell` to `is_sealed_authority_type_name`.
One line, and it would silently overturn M7 decision 17 across five
unrelated rules — refusing an `@actor` field that is legal today, refusing
the type inside a `@layout`, and inventing a consume-on-every-path
obligation for a value with no sink. **Rejected:** making it a rule for
every `pub` actor/driver method rather than a messageable driver's. An
`@actor` may own and pass its own cell; the hazard here is *this* driver's
ISR channel escaping, and a non-messageable driver's `pub` method is
unreachable — the same reachable-set argument decision 21 already makes.
**Rejected (option (b), recording it since it was offered):** blessing the
cell as exported surface. Nothing in 03 or 05 asks for it, `pub fn
pending_bits(read self) -> u32` exports the value with none of the
question, and "sole channel" is not a phrase to widen by omission.

### Decision 24 — both M7 guards are deleted, not narrowed

The two post-closure guards (`err-pool-two-devices`,
`err-pool-driverless-device`) refused images the language allows, because
the `BlkPool` mapping line carried no device and `wrela-vmm` handed every
window to its one `BlkDevice`. That is an artifact defect, and item P
fixes the artifact. Once the line names its device and
`GuestMem::window_offset` admits only that device's windows, **neither
refused shape is wrong any more** — so neither guard is narrowed; both are
removed, and each relaxation is pinned by the accepting golden that
replaced its `err-` case (`check-pool-two-devices`,
`check-pool-driverless-device`).

**Rejected: keep refusing a pool on a driverless device, on 03 §1
capability grounds** ("capabilities are minted while the image binds a
declared device to a `@driver`"; a device nothing binds mints nothing).
The argument is real but does not single out that shape: it applies
identically to a device with a pool and *no* driver at all, which is
`golden/boot-dma-pool` — a deliberately pinned, legal M7 shape. Applying
it uniformly would be a **widening** of the refused set, the opposite of
this item's remit, and would need its own normative sentence in 03 plus
its own clause. And the guard's actual shape — driverless *and* some other
device is driven — has no principle behind it once mapping is per-device;
it was a proxy for "there exists a model that would wrongly receive this
window", and none would.

**Rejected: keep the two-devices guard until a second device *model*
exists.** Its cost is paid by the language (a legal image refused) and its
benefit was already delivered by the report-format change. A refusal whose
stated reason has been fixed is the stale note this plan's own rules
forbid.

What 03 §1 does refuse is unchanged and lives one pass later:
`check_dma_pool_mint` rejects a driver bound to device#Y taking
`DmaPool[P, N]` for a pool declared reachable from device#X
(`golden/err-dma-pool-mint-wrong-device`). The mint rule and the
reachability rule are different rules; neither implies the other.

### Decision 25 — blk configuration belongs to the blk device

Legalizing two devices split a question that used to have one answer.
`blk_capacity_sectors`/`blk_accepted_features` scan the device list in
declaration order, and the *lowerer* reads the first through
`TypedProgram::blk_capacity_sectors`, where no `VirtQueue.configure` site
is in scope to disambiguate with. With two devices, "the device that
declares `capacity_sectors=`" and "the device whose pool hosts the ring"
are different questions.

**Rule:** `eval::image_checks::check_blk_config_names_the_blk_device`
refuses `capacity_sectors=`/`required_features=` on any device that is not
the blk device (`golden/err-blk-config-on-another-device`). 06-machine.md
§6's device set is closed and machine v1 has exactly one `blk`, so the
report's `BlkDevice device=device#N` line can carry only that device's
configuration. Silent for an image with no configure site: no device is
the blk device yet, and refusing on a guess is the fail-open this exists
to avoid.

**Rejected: a second, device-scoped derivation** beside the graph-wide
one — two derivations of one fact that can disagree, in the one place the
disagreement is invisible (the lowerer emits a build constant; the report
emits a line). **Rejected: leave it** — verified by mutation that with the
check disabled, `err-blk-config-on-another-device` builds and renders
`BlkDevice device=device#0 capacity_sectors=64`: device#0's line carrying
device#1's number.

### Decision 26 — `GuestMem` holds every window and carries one device

`GuestMem` is constructed with the **whole** declared window list plus the
index of the device whose view it is; `window_offset` refuses
`w.device != self.device`.

**Rejected: filter the window list at construction** (hand each device
only its own windows). Identical accesses succeed and fail, but the device
check becomes **vacuous** — nothing is left in the list to refuse, no
mutation of `devices.rs` could be caught by a boot, and the negative
oracle would be proving that an address is in no window rather than that
it is in *someone else's*. **Rejected: thread a `device: u64` argument
through `window_offset` and every `GuestMem` accessor** so one `GuestMem`
serves all devices: a much larger diff across a file item G is also
editing, and it creates a way to pass the wrong device id at a call site.
One `GuestMem` per device model makes that unrepresentable.

Consequence recorded: the `BlkDevice::new` config-time ring check and the
access-time check are two callers of **one** predicate (`window_contains`,
which gained the same device term), not two rules.

### Decision 27 — `own[P] T` stays device-untyped at build time

The negative boot is constructible only because nothing at build time
forbids handing a driver a payload handle from another device's pool: 03
§1's mint rule constrains the `DmaPool[P, N]` *capability* argument, and an
`own[P] T` payload handle carries no device in its type.

**Rule:** leave it that way. 03 §3's sentence is about what a device may
*reach*, which is a property of the mapping and is enforced where reaching
happens. A build-time device rule on `own[P] T` would be a second
enforcement of the same sentence whose only practical effect is to make
the first one untestable — the exact "build-time argument" this item was
told not to settle for.

**Rejected: add the rule and demote the boot oracle to a unit test.** The
M7 guards already were that, and the reason item P exists is that a
build-time refusal stood in for a runtime property nobody had tested.
Recorded so it is not forgotten: a future item that wants the build-time
rule too must keep a boot that still exercises `ForeignPool`.

## Decisions recorded (item C2)

### Decision 28 — one ring per (sending core, target mailbox root), and same-core edges do not use one

04 §3 says the lowering is a **bounded SPSC ring**, and SPSC means single
producer. Two actors on core 0 that both message one actor on core 1 are
two *senders*, and keying the ring by sender would give a per-actor ring
whose only purpose is to preserve a property the machine already has:
04 §2 puts exactly one cooperative loop on each core, and decision 11's
baton means exactly one vCPU is inside `hv_vcpu_run` at any instant, so
two actors on one core can never be mid-enqueue simultaneously. **The
producer is a core.** So the ring is keyed by `(sending core, target
mailbox root)` and the report says which
(`Ring kind=request src=0 dst=1 target=Sink ...`);
`golden/boot-cross-core-two-senders` is the oracle, and it pins exactly
one request-ring line for two senders.

Keying by target *root* rather than by target core is what makes the ring
free: a ring feeding exactly one mailbox has that mailbox's own slot
format, so the cross-core producer is literally `build_rt_enqueue`'s body
(`build_ring_enqueue`, shared verbatim) and the consumer hands each
message to the *same* `__rt_enqueue_<A>` a same-core send would have
called. There is one admission implementation in the machine, not two
that must be kept in agreement — which is how 04 §3's "identical message
semantics" is structural here rather than a claim.

**Same-core edges keep the mailbox path**, as §3's own last sentence
requires ("Same-core edges keep every as-if fast path of §6"). Nothing is
routed through a ring for uniformity: codegen emits one symbolic
`__rt_enqueue_<A>` call for every `send`/`await`, and *layout* redirects
it to `__rt_xsend_<src>_<A>` only when the call site's core differs from
the target's (`resolve_cross_core_edge`). Codegen never learns which it
got.

**Messageable `@driver`s** (item D) are ordinary ring *destinations* and
never ring *sources*: shape decision 2 keeps `@driver` on core 0 and C1's
own arm refuses one placed elsewhere, so an actor on core 1 may message a
driver on core 0 over a ring and the reverse cannot arise. 04 §3's "a
`@driver`'s vectors, pools, permits, and recovery lanes live on its core;
there is no cross-core hardware state" is not in tension, and not because
anything filters it: a ring slot carries a method index, a waker, and that
method's own argument words, and item D's own decisions 20/21/23 already
refuse a capability, protocol state, or `InterruptCell[T]` in a driver
mailbox signature. No hardware state can be spelled into a slot.

**Rejected:** one ring per ordered core pair, carrying a target-actor
index in each slot. It needs a wider slot than any mailbox, a per-slot
argument-count word, and a dispatch chain in the drain — three mechanisms
bought to merge queues that are already exactly as deep as the mailboxes
they feed. **Rejected:** one ring per sending *actor* — see above; it
buys nothing the baton does not already give, and multiplies rings by
actor count. **Rejected:** route every edge through a ring, same-core
included, "for uniformity". It would move every M5–M7 boot's rtdata and
rtcode, add a queue hop to the only path M6 measured, and delete §6's
as-if fast path that §3 explicitly preserves.

### Decision 29 — request and reply are separate lanes; a full ring is a rejection, a full mailbox is back-pressure

A reply is an edge in the other direction and rides a ring too — a
completing turn never stores into another core's turn record. But the two
directions cannot share a lane, because they fail differently:

- a **request** that does not fit has a caller to tell. A full ring
  returns 1 from `build_ring_enqueue` without touching `tail`/`count`,
  which is 02 §9.4's `NotAdmitted`/`Rejected` path at this ABI
  granularity, and the sender's already-emitted rejection handling fires
  unchanged (`golden/boot-cross-core-ring-full`);
- a **reply** that does not fit has nobody to tell. So it gets its own
  lane, sized so full is unreachable: a reply ring `d -> s` is as deep as
  the number of turn areas on core `s`, and a turn area holds at most one
  in-flight activation (04 §2's non-reentrancy) and therefore at most one
  outstanding `await`. `BRK_XREPLY_RING_FULL` is the guard on that
  argument, in the same class and with the same treatment as
  `BRK_REPLY_SLOT_NO_WAKER`.

**Capacity comes from the sealed graph, always.** A request ring is as
deep as the mailbox it feeds; a reply ring as deep as the destination
core's turn areas. An edge whose capacity cannot be derived — a target
declaring `mailbox=0`, or a sending core owning no turn area — is a build
error naming the edge. No silent truncation and no spin-until-space.

**A full mailbox back-pressures rather than drops.** The drain hands each
message to `__rt_enqueue_<A>`; if that is rejected the message stays in
the ring and the lane stops. The ring then fills, and the *next sender* is
rejected at its own send site — the rejection surfaces where a caller can
see it, one hop later. Nothing is ever admitted twice or dropped.

**Rejected:** one lane with a `kind` word. A stalled request lane would
sit in front of a reply that has nowhere to go, which is a deadlock built
out of the one queue that must never block. **Rejected:** a reply ring
that rejects. There is no caller left to hand the rejection to — the
awaiting turn is parked and the completing turn has already run. **Rejected:**
dropping a rejected message at the drain and reporting success to the
original sender. That is the silent-wrong-answer class, and it is what
back-pressure exists to avoid.

### Decision 30 — the waker carries its core in its top bits; the wake is one bit and decides nothing

A completing turn must know whether its waker's turn record is local. The
mailbox slot is `(method index, waker, args...)` and the turn record has
six words; widening either would move every report golden in the corpus
for a fact only cross-core images need. Guest-physical addresses in this
machine's layout are all below 2^31, so **the waker's top three bits are
free**: a cross-core send tags the waker with `src_core + 1`
(`waker_tag`), and `+1` rather than the bare index is what keeps "no tag"
and "from core 0" distinct. Untagged means local, which is what every
same-core send and every single-core image already writes, so those paths
are byte-identical rather than merely equivalent.

The **wake** is bit 0 of the destination core's pending word
(`pending::core_word_addr`) — 06 §5's doorbell, "a shared-memory word, no
trap" — raised *after* the message is published, never before. It is not a
ring-private vector bit, and that is deliberate: 04 §2 requires wakes to
be idempotent and the park primitive to have mask–arm–recheck semantics,
so the pending word is a "something changed, re-derive readiness from
memory" signal and nothing more. A woken core drains its rings because its
loop always does, not because a bit told it which. Correspondingly a
secondary core **clears its own pending word first, then drains**: a wake
landing during the drain re-raises it, so the core does not sleep on it,
and re-running the drain is idempotent.

**Rejected:** a third word in the mailbox slot holding the origin core.
Correct, and it moves `slot=` in every report golden that has an actor —
paying corpus-wide for a cross-core-only fact. **Rejected:** a seventh word
in the turn record. Worse: `TURN_RECORD_SIZE` is a codegen constant every
async frame offset is derived from. **Rejected:** a dedicated ring vector
bit in the pending word. It would make the wake carry information, which
is exactly what makes a wake losable; and device-owned bits are already
`1..=63` by M7 decision 12, so it would need reserving.

### Decision 31 — what C2 still refuses, and where the deadlock diagnostic went

Two shapes are refused rather than approximated, both reachable only in a
cross-core image, each naming the fn, the cores, and what lifting it
costs:

1. **An aggregate reply across a core boundary**
   (`golden/err-cross-core-aggregate-reply`). The aggregate arm loads
   `[waker + OFF_TURN_REPLY_SLOT]` and lets the callee write straight into
   the awaiting frame through `x8`. Deleting the refusal and running the
   gate showed the first reason immediately: the waker there is
   core-tagged, so that load dereferences the tag
   (`FAR_EL1=0x2000000040501660`). Untagging it is one line, which makes
   the second reason the real one — even untagged it is a direct
   cross-core store with no publication this compiler placed, and under
   decision 11's baton **no oracle here could show it broken**. Refusing
   an untestable claim beats shipping one.
2. **A checkpoint (loop back-edge) inside a turn placed on a secondary
   core** (`golden/err-cross-core-checkpoint`).
   `__wrela_checkpoint_service` names core 0's pending word by a baked-in
   constant and clears the whole word; servicing one from core 1 would eat
   the wake a reply ring just raised for core 0. That is the one way this
   item could still lose a wake, and 06 §5's mask–arm–recheck exists
   precisely so a wake cannot be lost. Lifting it is per-core checkpoint
   services plus the per-core deadline word they imply.

**The deadlock diagnostic moves for cross-core images.** M6's entry driver
prints `DEADLOCK_MSG` when nothing is ready, no deadline is armed and the
root is incomplete. In a cross-core image "nothing ready *here*" is not
evidence of deadlock — another core may be one turn from pushing a reply —
so core 0 parks unconditionally instead, and the VMM's own
`core N parked and no core is runnable` becomes the diagnostic. It already
fails closed with a named line rather than hanging. Single-core images are
untouched, down to the word.

**A found defect, recorded because the mutation found it and reading the
diff did not.** The VMM's core-0 park had a runnable-sibling shortcut that
yielded *without* marking core 0 `Parked`. That left core 0 eligible for
the baton whether or not anything ever woke it — so mutating `waker_tag`
to drop its `+1` (which makes every cross-core reply take the local store
path and raise no wake at all) still booted **green on every golden**. The
wake was decorative. The fix is ordering: in a cross-core image core 0's
no-deadline park is handled *before* the sibling shortcut and marks
`Parked` like any secondary, so resumption goes through the pending word,
which is where the machine's contract puts it. The same mutation now fails
two boots by name.

**Rejected:** keep the sibling shortcut and accept that the wake is
untested. That is exactly item C1's own recorded lesson (its first boot
golden survived a mutation because the mechanism under test was
decorative), and repeating it knowingly would be worse than making it.

## Decisions recorded (item F)

### Decision 36 — quiescence is the device's own answer, taken on the reset path's trap

03-hardware.md §9 gates reclaim on quiescence — "per-queue reset (when
negotiated) or full reset establishes quiescence, and only then is memory
reclaimed" — and M7's reset established nothing: `emit_device_reset` bumped
a guest-side epoch word and the device model was never told. A guest that
bumps a word and calls it quiescence has proved exactly nothing, and item
G's own report names the failure mode ("its first boot golden survived a
mutation because the reset in it was decorative"). On this machine the
device *is* the VMM, so only the VMM can say it has stopped.

**Rule:** `RunningDevice.reset` performs a trapping store to a new
`mmio::QUIESCE_MMIO_ADDR`, naming this queue's own quiesce-count word,
**before** it bumps the epoch. The VMM refuses any other address
(`BlkFault::QuiesceWrongWord`) and refuses a quiesce on an image with no
`blk` device; otherwise it stops its model using the ring and increments
the count word in guest memory. `SLOT_BOOK_QUIESCED` is the one word on
this machine that nothing in the guest ever writes, and it is the whole
evidence base for a reclaim.

No `docs/language/` edit was owed: 06-machine.md §5 already blesses this
exact trap in the sentence that forbids hot-path ones — "MMIO-shaped
register access exists only on setup/**reset** paths, where a trap is
fine" — and no normative text names the MMIO addresses. The constant
follows `PARK_MMIO_ADDR`/`RELEASE_MMIO_ADDR`'s one-page-per-register
convention exactly.

**Rejected:** keep quiescence guest-side (bump a counter in the reset's own
codegen and gate on that). It passes every oracle a mutation of the *guest*
could break and is a fiction: the count would be written by the same
compiler that reads it, so "the device has stopped" would be a statement
about the driver. **Rejected:** a shared-memory quiesce request word the
VMM notices at its next doorbell poll — a poll needs a polling site, the
only sites are vCPU exits, and the guest then has to park and re-check, so
it degenerates to this trap with a park bolted on (`RELEASE_MMIO_ADDR`'s
own rejected alternative, one item earlier). **Rejected:** have the VMM
quiesce on some *other* signal (an epoch write it watches) — nothing
watches guest memory except at exits, same argument.

### Decision 37 — quiescence is *finish, then stop*, not *drop*

Given the trap, what should the model do? A hardware reset drops
outstanding work: the device stops, and buffers it was given are simply
never written. That is the first thing this item implemented, and running
it broke `golden/err-boot-epoch-stale` — M7's own oracle for
`hardware.reset.epoch-invalidates`, in which a completion that was
legitimate before a reset arrives after it and is refused as `StaleId`.
With chains dropped, that completion can no longer exist, and the golden
failed its own assert instead of aborting.

That is not a golden getting in the way; it is the docs disagreeing with
the reading. §9 spends a clause on stale completions surviving a reset
("producing a new epoch that invalidates all prior receipts"), so a reset
on this machine is not allowed to make them unreachable.

**Rule:** `BlkDevice::quiesce` **finishes** every chain the guest has made
available — synchronously, while the vCPU sits in the trap, with the
completions going through the ordinary recorder and used-ring path so a
straggler still surfaces and still meets the epoch check — and **then**
stops: `last_avail_idx == avail.idx`, doorbell clear, after which no
descriptor published before the call can ever be walked. It ignores the
doorbell when finishing, because "the doorbell had already been consumed"
is not an answer a driver can act on. Only then is the count incremented.

Finishing is also strictly stronger for the property the count exists to
certify: the device is provably *done* with the buffer rather than
provably never going to start.

**Rejected:** drop the chains and re-home `err-boot-epoch-stale` to some
other shape. The shape does not exist — a stale completion needs a device
that completed pre-reset work, which is the thing dropping deletes.

### Decision 38 — quarantine is a flag plus a stamp, and it is unconditional

04 §4 quarantines "affected regions and pool slots"; §9 forbids reclaiming
possibly device-owned memory. Both need the recovered slot to be in a state
that is neither "in flight" nor "free".

**Rule:** `recover` raises `SLOT_FLAG_QUARANTINED` on the slot's meta record
and copies the queue's live quiesce count into
`SLOT_BOOK_QUARANTINE_STAMP`. `reclaim` is then one compare: equal counts
mean no quiescence has happened since the quarantine.
`virtqueue::reclaim_gate` is the pure function, `codegen::emit_queue_reclaim`
emits it compare for compare, and its two refusals are separately named.

Quarantine fires on **all three** `CompletionOutcome`s, including
`Completed`, where the descriptor demonstrably did come back. Making the
gate outcome-dependent would put the fail-open reading one branch away from
the fail-closed one for no fact §9 asks for, and it costs a reclaimer one
reset it was going to perform anyway.

**Rejected:** a free-list, so a reclaimed slot returns to a pool rather than
to a named handle. That is M7 decision 20's deferred multi-flight work and
would move `SLOT_BOOK_BYTES` for every image, not only the ones that
recover. **Rejected:** clear the quarantine at the *reset*, so `reclaim`
needs no book word at all — it makes the gate an ordering coincidence
rather than a checkable fact, and a `reclaim` on a queue nothing
quarantined would silently hand back a stale address.

### Decision 39 — `reclaim` declares its brand with two bare names

`claim` gets `P` from the `Receipt[P]` it consumes. `reclaim` cannot:
`recover` already consumed the receipt (03 §5 — a receipt resolves exactly
once and dropping one is illegal in every state), and with it the only
value carrying the payload's brand.

**Rule:** `queue.reclaim(pool=P, payload=T) -> own[P] T`. Both arguments are
bare names with no value form — a bound pool name (02 §4) and a
`@layout(dma)` struct — and they are resolved by building the ordinary
`own[P] T` ast node and handing it to `mctx.resolve_type`, so an undeclared
pool and a non-`dma` payload are the same two diagnostics they are in any
annotation. It is the same pair `img.dma_pool[T](name=P, ...)` declares
when the pool is created.

What the declaration cannot lie about is the bytes: the address handed back
is the quarantined slot's own payload word. It decides only which pool the
language believes the handle belongs to, and pool names have no runtime
representation. Checking that against the queue's device at build time is
deliberately *not* added — the identical trade item P recorded as decision
27, and adding it here would be a second enforcement of a sentence whose
first enforcement is the address itself.

**Rejected:** infer the type from an annotated binding
(`b: own[P] T = queue.reclaim()`). It works — `check_assign` already
threads the expected type — and it makes the fact that decides the handle's
brand *optional syntax*, which is the wrong place for it. **Rejected:**
`queue.reclaim[own[P] T]()`. The bracket form parses its contents as
expressions, and `own[P] T` has no expression form, so it needs parser work
plus a second dispatch shape in both `bodies` and `access` — new grammar to
buy a spelling. **Rejected:** returning the payload from `recover` after
all — item G's decision 17 refused exactly that, and it is still right: a
value that must not be handed back on `Unknown` should not be in the
signature that reports `Unknown`.

### Decision 40 — the subset, and what stays fail-closed

Item F's mandate is the largest unclaimed area in the milestone and 04 §4
specifies a full teardown order. This item built the **reclaim** half end to
end and deliberately built none of the rest.

**Built:** host-confirmed device quiescence on the reset path; quarantine of
the recovered DMA slot; quiescence-gated reclaim, with an HVF boot whose
second publish is impossible without it (`count=1`, no spare) and a
one-line-deleted negative twin that aborts by name.

**Not built, each fail-closed with a named owner:**

- 04 §4's **generated highest-band recovery turn** and the whole teardown
  order (close admission, cancel child registrations recursively, transfer
  in-flight receipts, cleanup nodes in reverse source order, resolve
  `Cancelled` only when the cleanup graph is empty). New explicit gap
  `hardware.cancellation.recovery-turn`, with its flip condition written
  out. It is also *unreachable* today: a `Receipt[P]` lives only in a
  driver field, because caller-side `await receipt` does not execute (item
  E), so no cancellable frame can hold one.
- **Region quarantine.** Only DMA slots are quarantined; a group's or
  pool's region is untouched. Named in the new clause.
- **§9's declared quiescence bound** and its "quarantine the device and
  pool under an explicit policy" alternative. Quiescence here is
  established synchronously inside a trap, so there is no window to exceed;
  the failure mode is the VMM refusing, which fails the boot closed — §9's
  "goes target-fatal" arm. The policy arm has no implementation and no
  source surface.
- **Sibling epoch-carrying reset errors.** A single-flight queue has one
  slot, so "every affected owner" is one owner, and that owner does get the
  epoch-carrying error (`recover` reports `Unknown`). The sentence is
  satisfied at n=1 and untested above it; siblings need M7 decision 20's
  free-list.
- **Image-fatal abandon** (M6 decision 12 / M7 decision 8 / shape decision
  4) is **unchanged**. This item lifted the reclaim floor, not the
  supervision one, and shape decision 4's "not a silent change to that
  floor" is honored by not changing it at all.

**Rejected:** build a partial teardown — say, closing admission and
quarantining, but not the recovery turn. A teardown that silently skips a
step is worse than an absent one, because the absence is a gap the ledger
counts and the partial is a promise the code does not keep.

## Decisions recorded (item C3)

### Decision 42 — the recorder **witnesses** admission; it does not inject it

This is the decision the item's own brief demanded be made explicitly, so
it is stated in the two words it asks for and the evidence is named.

**What shipped: witness-only.** A cross-core admission is performed by
guest code — `layout::build_rt_drain` pops a ring slot and calls the same
`__rt_enqueue_<A>` a same-core send would have called — in guest memory,
with no trap (06 §5: hot paths never trap). The VMM therefore cannot
*perform* an admission, and it does not *feed* one back either: nothing in
record or replay mode writes a mailbox, a ring, or a head/tail/count word.
The recorder reads each request ring's **occupancy word** at every vCPU
exit and emits one `ChoiceEntry::Admission` per message the core that just
ran admitted. Under replay the identical witness runs and the witnessed
entry is compared against the recorded one; a disagreement is
`Divergence::AdmissionMismatch`, named exactly like `DeviceCompletion`'s.
**Divergence detection is the entire enforcement.**

**Why injection would be a claim with no mechanism.** Decision 11's baton
means exactly one vCPU is inside `hv_vcpu_run` at any instant, so the
admission order at each mailbox is a deterministic function of guest state
today. There is no alternative order to inject, and a "replay injects the
recorded order" claim would be untestable in exactly the way decision 31
already refused an untestable claim for the aggregate reply. Injection
becomes meaningful the day something *varies* the order — the schedule
enumerator ROADMAP names, which would vary the baton hand-off. That is the
same `Chooser::choose_next` seam M6 bought for it; nothing here forecloses
it, and the entry format is exactly the one an enumerator would drive.

**Why the count is exact rather than sampled**, which is the part that
could quietly have been wrong. A ring's producer and consumer are
different cores (`parse_report` refuses `src == dst`), and at most one core
ran between two consecutive exits. So for any one ring, that core is either
its producer or its consumer, never both — and a ring whose *consumer* just
ran can only have shrunk, by exactly the number of messages that core's
drain admitted. No modular head arithmetic, no lost wrap. If a consumed
ring is ever seen to grow, the boot fails closed by name rather than
under-recording. The **order** is exact for the same reason:
`build_rt_drain` walks its inbound lanes in `RuntimeTables::rings` order,
draining each to empty before the next, and nothing else can produce into
them meanwhile — so walking the report's `Ring` lines in that order
reconstructs the order the guest actually admitted in.

The report's `Ring` line gained `base=` for this: 06 §8 makes the VMM the
recorder of per-mailbox admission order, and the report is the VMM's whole
configuration, so a ring the VMM cannot address is one whose admissions it
cannot witness. Three report goldens moved, by exactly that field.

**Rejected:** a trapping "admission doorbell" the guest rings per
cross-core message, so the VMM observes each admission directly. It is a
real injection-capable mechanism and it is a VM exit on the hot path, which
06 §5 forbids by name — buying an observation the machine already makes
observable in memory, at the price of the property the machine is designed
around. **Rejected:** reconstructing from the ring's `head` index. It wraps
modulo capacity, so exactly `capacity` messages between two observations
read as zero; `count` needs no such reasoning. **Rejected:** recording
reply-ring deliveries as admissions too. A reply is delivered to a turn
record, not admitted to a mailbox; §8 says "per-mailbox", and a tag that
meant two things would make the sequence less enumerable, not more.
**Rejected:** widening `ChoiceEntry::Admission`'s fields (a sequence
number, a slot address) to make each entry unique. The position in the
sequence *is* the order — that is what an enumerable choice sequence
means — and every added field is a format migration for pre-M8 recordings
plus a new way for the log to carry host bookkeeping.

### Decision 43 — `sender` is a core, and the M6 field set is kept byte-for-byte

Decision 9 spelled the entry `(mailbox, chosen sender)` and decision 28
later settled that a cross-core ring's producer is a **core**, not an
actor: two actors on core 0 messaging one actor on core 1 share one ring,
because the per-core loop plus the baton make simultaneous enqueue
impossible. So the honest filling of `sender` is `core<N>`, and the honest
filling of `mailbox` is the ring's target mailbox root — the ring feeds
exactly one, which is what makes its slot format that mailbox's own.

The field set is therefore unchanged from M6, and deliberately so: every
recording written before this milestone still parses, the pinned format
test needed no new expectation beyond its rename, and 06 §8's enumerable
choice sequence keeps carrying no timestamp, no address, and no
interleaving trace.

**Rejected:** naming the sending *actor*. It is not knowable from the ring
(the slot carries a method index, a waker and argument words, not a sender
identity), and inventing it would mean either a wider slot in every
mailbox — decision 30 already rejected paying corpus-wide for a
cross-core-only fact — or a guess.

### Decision 44 — the named workload is new, because no existing image could falsify an *order*

`boot-cross-core-two-senders` looks like the obvious workload: two
cross-core messages, one mailbox. But both of its senders sit on core 0, so
both recorded entries read `Admission mailbox=Sink sender=core0` and
**swapping them is unobservable** — the strongest tamper the corpus could
express would have been "change one field to a value nothing produces",
which is a weaker oracle than the item asks for.

`golden/boot-cross-core-admission-order` puts `Near` on core 0 and `Far` on
core 2, both messaging `Sink` on core 1, so `Sink`'s admission sequence is
`core0` then `core2` — two entries that differ and an order a tamper can
invert. `Far` uses a proven bare `send` rather than an `await` because
decision 31 refuses a checkpoint inside a turn on a secondary core, and an
`await` is one; a `send` needs none, which is how a secondary core can
produce into another core's mailbox today.

**A fact this workload made visible, worth recording because it is the
reason the entry is interesting at all.** Core 2's message is *published*
first (the root awaits `Far.kick` before it awaits `Near.go`) and is
*admitted* second, so `Near`'s await returns 1 rather than 11. Admission is
performed by the **consuming** core's drain, which walks its inbound lanes
in ring order and empties the `src=0` lane before it looks at the `src=2`
one. Publication order is a property of the producers; admission order is a
property of the consumer. That gap is exactly what 06 §8 asks the recorder
to log, and this is the smallest image in which the two visibly differ.

### Decision 45 — one writer for the VMM-facing report lines (a found defect)

`xtask`'s own hand-built runtime report — the one every determinism lane
boots (`repro`, `bench guest`, `diff-eval`) — emitted only `Machine
revision=`/`Input path=`/`Section name=`/`Entry base=`. It had **never**
carried item C1's `CoreEntry` lines, nor M7's `Blk*`/`IrqHostInject` ones,
while `bin/wrela.rs`'s runtime tier carried all of them. So no image built
by a determinism lane could be multicore: `golden_test_image` on a
cross-core case produced a report claiming one core, and the boot died at
the release doorbell ("core 0 released 3 core(s) but this image's report
declares 1"). It was invisible because every case those lanes had used
until now was single-core.

Fixed by collapsing the copies rather than adding a fourth:
`layout::append_vmm_runtime_lines` emits every line the VMM's
`parse_report` consumes past the preamble, and `bin/wrela.rs` plus both
`xtask` writers call it. The `Ring` lines themselves have one renderer
(`ring_report_lines`) shared with `--stage=report`, so the runtime report
and the pinned artifact cannot disagree about a ring.

**Rejected:** teaching `xtask`'s copy the two new line kinds it needed and
leaving three copies. The drift was found by an item that had no reason to
look for it, which is the argument for deleting the class rather than the
instance.

## Decisions recorded (item E)

### Decision 32 — the handoff call is uncomposed, and the caller-owned receipt is the caller's own turn record

03-hardware.md §5 defines a *calling convention*, not a method: "any public
synchronous `@driver` method with exactly one `take p: P` parameter and
result `Receipt[P]` receives the handoff calling convention", and it states
the result by name. 02-language.md §9.4 describes the ordinary awaitable and
composes `declared R -> Result[R, CallError[never]]`. The two disagree for
exactly one signature, and item E resolves it the way GOAL.md's
doc-contradiction rule says to: the specific rule wins, and §9.4 gains one
paragraph saying so (REVIEW-QUEUE'd, clause
`actors.calls.callerror-composition`).

**Rule:** `await handle.m(...)` where `m` is handoff-shaped on a `@driver`
has type `Receipt[P]`. One predicate decides it —
`sema::handoff::is_handoff_signature`, the same one that already prints
`handoff fn ...` in the check dump and enforces the `publish`/`reject` body
rule. Everything else is unchanged: an ordinary mailbox admission, an
ordinary park, an ordinary scalar reply word.

This is not ergonomics. **With the composition the convention is unreachable
from source**, verified by mutation rather than argued: restoring it makes
`golden/boot-receipt-handoff` fail to type-check, because the receipt is
sealed inside a `Result` the language cannot open at that point —
`flowwir_lower` refuses a `match` containing an `await` in an arm, and
`CallError` is not a source-nameable type so `?` cannot convert it. Those
are two real floors of their own; neither is this item's to lift, and
neither is papered over here.

**And the admission side needs nothing built.** §5's "admission commit
atomically moves `P` into the message *and* installs the caller-owned
receipt, before the handler runs" is `layout::build_rt_enqueue` read for
what it already does: between the capacity test and the `count += 1` that
commits the slot it writes the method index, the **waker — the caller's own
turn area, which is where the receipt will land** — and then the payload
words, with no checkpoint, no scheduler entry and no other turn in between.
The driver's `return queue.publish(...)` transitions that pre-existing pair.

**Rejected:** a separate caller-frame receipt *cell*, published through
`OFF_TURN_REPLY_SLOT` before the enqueue and written by the handler through
`x8` (item D's handoff note points at this shape). It works, and it is what
this item started building. It was dropped because it buys **no observable
behaviour**: the cell would hold the same word the reply slot holds, and no
caller can look at it any earlier, because the caller is parked until the
handler's turn completes either way. Against that it costs a second
representation of `Receipt` — a sealed type whose "one opaque word"
property `codegen::is_aggregate` and `mwir::size_of` both assert and whose
agreement they are commented as depending on — plus an indirect return ABI
for it, plus a forwarding path in `build_rt_select_and_run_core`, which is
hand-assembled A64 and the one module ROADMAP M10 exists to delete. Spending
that in the most dangerous file in the compiler to relocate a word is the
opposite of the trade this project makes.

**Rejected:** a *bare* (non-`await`) handoff call, `r = disk.submit(...)`,
which reads closer to §5's "before the handler runs". It would suspend
anyway — the caller cannot have the receipt until the handler has published
— so it would be a suspension invisible in source, in a language whose
premise is that suspension points are spelled. **Rejected:** keeping the
composition and lifting `match`-with-`await` in `flowwir_lower` instead —
that is a state-splitting feature across arms, an item of its own, and it
would still leave §9.4 and §5 disagreeing about the type.

### Decision 33 — a handoff reply is not probed, because its payload is already a parameter

`layout::check_driver_message_surface`'s reply arm was item D's floor and
named this item. It is not loosened into a payload probe; for a handoff
method it is **skipped entirely**, and the reason is structural rather than
an exemption: §5's signature is "exactly one `take p: P` parameter and
result `Receipt[P]`" — the *same* `P` — so the parameter loop directly above
has already walked the whole payload, with the same leaf set and the same
`Option`/wrapper/cycle reach. Probing `Receipt[P]` again could only ever
refuse the `Receipt` wrapper, which is the convention itself. The `@task`
and ISR arms below it are deliberately *not* skipped: a `pub` `@task` is
synchronous and would otherwise be handoff-shaped by signature.

The parameter direction stays refused, and working it corrected item D's
belief about *where*: `sema::types::validate_fn_capability_types` already
rejects a `Receipt` parameter on every `pub` method of every
`@actor`/`@driver`, messageable or not — its `Receipt` whitelist was only
ever for the reply position. So the layout-tier parameter arm is
**unreachable** for a receipt. `golden/err-driver-message-receipt` is
retargeted onto the real diagnostic rather than deleted, and 05-library.md
§2's sentence is narrowed to match ("no message parameter carries a
receipt", with §5's reply named as the exception).

**Rejected:** deleting `err-driver-message-receipt`. The floor's name is
where a reader looks for what happened to it; the golden's diff is the
record that the refusal moved rather than vanished. **Rejected:** keeping a
payload probe on the reply as defence in depth — this file's own precedent
(`type_contains_capability`'s "captures" note) is that an unreachable arm is
named, not written.

### Decision 34 — a `never`-typed statement ends its path

Found, not sought. 02-language.md §11 says `panic(message)` **abandons** the
actor — "the turn stops ... Abandonment is not catchable" — and the
normative worked example depends on it six times
(`docs/language/examples/virtio-storage.wr`: `panic("cache line has no
payload")` and friends). `sema::flow` did not know: `Stmt::Expr` always
returned a fallthrough, so a `panic` arm supplied neither totality for a
value-returning body nor an exit from a join. It had never bitten because
that example is a **parse-tier** golden (`golden/ast-virtio`) — nothing had
put a `panic` through the flow pass.

Item E hit it immediately, and structurally rather than by taste: 02 §9.2
requires `self` to be whole at every suspension, so a caller that lends a
DMA payload across a handoff must unwrap its `Option[own[P] T]` inside a
*synchronous* helper (`Option`/`is`/`match` are all unlowered in an async
body), and that helper's impossible arm has nothing to return.

**Rule:** a statement whose expression type is `Type::Never` has no
fallthrough. One line, one producer today, and `assert` — which is
conditional — is untouched. New clause `sema.flow.never-ends-the-path`,
oracle `golden/check-panic-diverges`, mutation-verified.

**Rejected:** working around it in the golden with an infinite loop or a
recursive call in the impossible arm — a placeholder a reviewer would
rightly read as the compiler being wrong, written into the corpus instead of
fixed. **Rejected:** widening it to a general reachability analysis — no
rule asked for one. **Left alone, named:** the example's *other* shape — a
name first bound inside one arm and read after the join — is `error[name]`
one pass earlier (`sema.names.resolution`'s scope-leak fix), `panic` or no
`panic`. That is a real doc/compiler disagreement on a parse-tier example;
naming it is this item's contribution, closing it is not.

### Decision 35 — a handoff `await` inside a group is refused by name, not resolved with a lie

02 §9.5: "Cancellation becomes observable at `await`." An ordinary actor
await resolves `Err(CallError.Cancelled)` into its composed result. A bare
`Receipt[P]` has no error slot, and the only word that fits is a receipt —
so a cancelled handoff would have to hand back a receipt for work nobody
submitted, which the caller would then `await` against a slot that is not
in flight.

**Rule:** `emit_await_resume` refuses a handoff await when the image
declares any `with group` (`gctx.arena_capacity != 0`), by name, in the
`unimplemented` category, pointing at 03 §9's recovery turn — plans/M8.md
item F. The condition is a whole-image fact codegen already has, so the
refusal is exact rather than conservative for group-free images.

**Rejected:** resolving the cancellation as an already-resolved receipt with
an error status — that is inventing a completion the device never produced,
in the one place 03 §9 is explicit that memory may still be device-owned.
**Rejected:** giving the handoff reply its own two-word `Result` after all —
that is decision 32's rejected composition wearing a different name, and it
would reintroduce exactly the shape the language cannot destructure.

**Thin / deferred (honest):**
- **The atomicity property §5 states is empty by construction, and that is
  the finding.** "A completion that arrives between admission and the
  receipt being installed must not be lost" has no window to test: the
  waker *is* the install, and it is written inside `rt_enqueue`'s own
  commit sequence with no checkpoint in it. What was built instead is an
  oracle for the window that does exist — completion between `publish` and
  the caller's park — and it is verified live in both directions by
  mutation. Stated rather than claimed as the doc's own sentence.
- **Exactly-once is a compile-time property on the caller side.** `await`
  consumes the receipt, so a double resolution is unrepresentable rather
  than survived. There is no runtime oracle for a caller double-resolving,
  because no program can express one. The driver-side half (a retired slot
  meeting a fail-closed abort) is item G's, unchanged.
- **A handoff `await` inside a `with group` is refused** (decision 35). The
  flagship shape does not use one; item F owns the repair.
- **`VirtQueue.reject` still mints 0**, so `await`ing a *rejected* handoff
  receipt would dereference a null meta record. Pre-existing (`lower.rs`'s
  own comment says so since M7) and untouched: `boot-receipt-handoff` never
  takes the reject arm, and no new golden reaches it. Naming it here rather
  than discovering it in item F.
- **The drain count is measured, not derived.** `drain_count == 3` for two
  handoffs; one handoff alone yields two. `drain` counts *wakes carrying a
  nonzero pending word*, and the constant extra wake belongs to the VMM's
  blk model, not to this item. The load-bearing half of that row is the
  mutation, not the constant.
- **Only one caller, one driver, one in-flight receipt.** The queue is
  single-flight by construction (M7 decision 20: one meta record), so
  nothing here says anything about two callers holding receipts at once,
  or about a receipt crossing a core boundary — that inherits whatever
  items C2/C3 land, and nothing here proves it.
- **`self` must be whole at every suspension**, which is why the caller's
  payload leaves and re-enters `self` only inside synchronous helpers. That
  is 02 §9.2 working as written, but it means the natural spelling
  (`match` on the `Option`, `await` in the arm) is unavailable in an async
  body — `match`/`is`/`EnumConstruct` are all `error[unimplemented]` there.
  Three separate floors, all pre-existing, all named rather than worked
  around.

### Attack 6 — handle-index collision: REAL HOLE (fixed)

at the resolver. A one-line revert of the driver arm breaks both.

**Collateral.** Every `Storage` that field-wired `disk=disk` without an
`init` had been relying on `driver#0 == 0` matching zero-fill
(`check_field_wired_args`); those goldens gained an `init`.

**Dispatch.** Still static-by-type — so this was an identity hole, not a
live mis-delivery. Identity is what a handle is; the day handles become
dynamic the colliding space would deliver to the wrong root.

### Attack 5 — cross-core into a driver mailbox: golden landed

`golden/boot-cross-core-driver-mailbox`: `Probe` on core 1 one-way-`send`s
into `mailbox=` `Stub` on core 0; the root then same-core-awaits
`Stub.count` and asserts `1`. Report pins
`Ring kind=request src=1 dst=0 target=Stub`. That line plus `count == 1`
is impossible unless the ring delivered into the driver's mailbox.

**Finding along the way.** An *await* from core 1 into the driver is
refused today: an await-resume is a checkpoint (06 §4), and decision 31
refuses checkpoints on a secondary core. Diagnostic:
`Probe.ask runs on core 1 and contains a checkpoint (a loop back-edge)...`.
Satisfiable lift: per-core checkpoint services (already named by decision
31). The send-shaped witness is what can run under today's floors; the
await shape stays closed on purpose.

**Residual.** `send_proof` still counts only `@actor` mailboxes for
capacity, so a bare `send` to a driver is never proven infallible (the
golden consumes the `Result`).

### Attack 4 — cross-core barrier under the baton: analysis + baton assert

**Why no barrier can be tested today.** Decision 11: three host threads,
exactly one inside `hv_vcpu_run` at a time (the baton). A missing
publish/acquire barrier between ring payload stores and the occupancy /
pending-word raise cannot reorder against a second core that is not
running. 04 §3's "sealed publish/acquire ordering" is therefore discharged
today by *store order in one thread* plus the baton, not by an AArch64
barrier instruction.

**What would test it (actionable later).**

1. **Hardware/VMM capability.** True concurrent `hv_vcpu_run` on two host
   threads under Hypervisor.framework — retire the baton (and accept that
   06 §8's choice sequence must grow an interleaving enumerator, which
   decision 11 rejected for M8).
2. **Witness program.** A store-store / load-load reordering across a
   ring's occupancy word and its payload: core A publishes slot payload
   then raises `count`/`pending` without a DMB; core B observes
   `count != 0` (or the pending bit) and reads the payload words. Under
   concurrent execution the payload can still be stale; under the baton it
   cannot.
3. **Barrier to emit.** AArch64 `DMB ISHST` (or `DMB ISH`) after the
   payload/`count` stores in `build_ring_enqueue` / `build_rt_xsend` and
   before the pending-word raise; matching `DMB ISHLD` (or full `DMB ISH`)
   after the pending-word clear / occupancy load and before payload reads
   in the drain. Belongs in `layout.rs`'s ring enqueue/drain assembly
   (and would need `encode.rs` to grow a `DMB` encoder if one is not
   already there). Owned by whoever lifts the baton — `codegen.rs` is not
   required if the ring bodies stay layout-owned.
4. **Why not a golden today.** No concurrent vCPU execution ⇒ no
   observable reordering ⇒ a golden that "passes with a barrier" would
   also pass without one. That is the exact class decision 31 refused for
   aggregate cross-core replies.

**What was mechanized now.** `crates/wrela-vmm/src/hv.rs` wraps
`hv_vcpu_run` with an atomic depth counter that `assert!`s the depth was 0
on entry. The baton invariant is therefore fail-closed rather than
believed: overlapping runs panic before a silent memory-ordering bug can
look green. Unit test `baton_run_depth_starts_at_zero` pins the quiescent
half. Ledger gap `machine.cross-core.publish-acquire-barrier` names the
barrier itself with the satisfiable condition above.
