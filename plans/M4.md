## Goal

`wrela build path/to/image.wr` "compiles" a wrela program: the module
graph is loaded as the transitive import closure of the root, imports
stop failing closed, the `@image` body runs in the M3 evaluator with the
builder intrinsics as its effects, the declared runtime graph is checked
(wiring, pools, supervision, restart provisions), and the **image
report** comes out as a byte-stable, diffable golden artifact — before
any runtime exists and with zero instructions emitted. No manifest, no
build configuration: the program is the single source of truth, and
every build-affecting constant lands in the report's build identity.

## The ROADMAP sentence, scoped honestly (decide once)

ROADMAP M4 says "the virtio example 'compiles' to a diffable report."
[virtio-storage.wr](../docs/language/examples/virtio-storage.wr)'s own
header says it is ASPIRATIONAL and imports modules the stdlib does not
ship; its bodies are full of `await`/`send`/`with`, which stay
fail-closed (async typing is not M4 — non-goals). The M4 realization of
that sentence is therefore: **an M4 example appliance** — a real
multi-module project with devices, drivers, actors (synchronous handler
bodies), pools, supervision, and restart provisions, built from the
shipping intrinsics — compiles to the pinned report. virtio-storage.wr
keeps its existing corpus guarantee (lexes + parses) and graduates to a
real build when the stdlib and async milestones supply what its header
names as missing. The plan records this so nobody quietly weakens either
side.

## Shape decisions (frozen by goldens — decide once)

1. **The build is pointed at the image root** (02 §2.1 as rewritten):
   `wrela build path/to/image.wr`. A module's declared path must agree
   with its file path; walking the agreement upward anchors the package
   root; disagreement is a named diagnostic. The module graph is the
   transitive import closure of the root — an unimported module is not
   part of the build (a separate whole-tree sweep is tooling for later,
   not this milestone). Loader errors (missing file for an imported
   module path, root outside any consistent package root, cycles —
   see decision 3) get one new fixed diagnostic category, `build`,
   added deliberately to the `SEMA_CATEGORIES` set.
2. **Imports resolve whole-program**: collect runs over every module in
   the closure first, then the existing pipeline sees a global symbol
   table (module path → public names). `from a.b import c` binds `c`
   locally; only `pub` items are importable; missing modules, missing
   names, non-`pub` imports, and collisions are named diagnostics. Sema
   stays one deterministic batch — modules loaded and checked in BTree
   order of module path, no laziness. `--stage` dumps stay per-file and
   byte-identical for single-module programs (existing goldens must not
   move). The `core` alias resolves into the toolchain `stdlib/` tree;
   anything imported from it that does not exist fails closed with the
   missing path (the stdlib ships nearly empty in M4 — that is the
   stdlib milestone's problem, not ours to fake).

   Sub-note (recorded at item A execution, 2026-07-23 — the plan did
   not pin this rule): locating `stdlib/` itself is two fixed candidates,
   in this order, no environment variable, no search path — (1) a
   directory literally named `stdlib` sitting next to the package root
   (a sibling of `pkgroot`), which is what lets a self-contained project
   (this milestone's own project-shaped golden fixtures included) ship
   its own `stdlib/`; else (2) the real toolchain `stdlib/`, baked in at
   compile time via `crates/wrela-compiler`'s own `CARGO_MANIFEST_DIR`
   (`.../../stdlib`) — wherever the compiled `wrela` binary is actually
   run from (`loader::core_root`). Both the missing-module and the
   core-miss diagnostic deliberately omit the resolved filesystem path
   from their message text (citing only the dotted module path
   instead): candidate (2) is an absolute path fixed at *this checkout's*
   compile time, and printing it would bake this checkout's own location
   into a pinned golden, breaking in any other clone or worktree.

   Sub-note 2 (same date): item A's own scope line on *consuming* an
   import beyond name resolution. An imported `const`/`fn` is fully
   usable as a value (called, referenced) and an imported `struct`/
   `enum` is fully usable as a value too (constructed, field-accessed)
   — `sema::check_program` splices each already-built `bodies::ModuleCtx`
   entry from the exporting module (independently built, needing
   nothing from any other module — which is exactly what makes import
   cycles free) into the importing module's own, under the local
   (possibly aliased) name, read-only reuse never a re-check. What does
   *not* land in item A: `types::declare`'s own type-name table stays
   module-local, so an imported `struct`/`enum` name used as an explicit
   type annotation (a fn param/return, a struct field, a `const`'s
   declared type) still resolves the bare *name* (`symbols::resolve`
   accepts it) but fails at `declare` with the ordinary `error[type]:
   unknown type` — a real, narrow, disclosed gap, not a silent wrong
   answer, left for whichever later item first needs cross-module types
   in a signature position. `pub from ... import ...` re-export is
   likewise not implemented (a module's own export table is only its
   own declarations) — no required golden needs either.
3. **Import cycles between modules are legal.** (Amended 2026-07-23 at
   execution start: this decision originally read "import cycles are
   errors", but 02 §2 — human-authored, normative, predating this plan —
   already says "imports are compile-time name bindings and run no
   code, so import cycles between modules are legal; cycles through
   constants, layouts, or image construction are errors". The original
   text's own escape clause — "that is a doc decision first" — resolves
   the contradiction: the doc wins, unrevised.) The loader's closure
   walk uses a visited set and terminates on cycles without complaint;
   the cycles that *are* errors stay covered where they live —
   const-initializer cycles by M3's evaluator, construction cycles by
   item C's DAG check. Rejected alternative: rejecting import cycles
   anyway, which would have required a doc rewrite to weaken a settled
   sentence. Golden: an accept project whose two modules import each
   other.
4. **Quotas stay language-defined constants** (02 §2.1/§12): no
   profiles, no overrides, no configuration surface. The constants are
   recorded in the report's build identity. An override mechanism
   arrives only with a demonstrated need — the cleverness-budget
   discipline applied to configuration.
5. **`@image` evaluation is the M3 evaluator plus intrinsic effects.**
   The builder surface (05 §9: `Image(name, target)`, `img.device[D]`,
   `img.driver`, `img.actor`, `img.pool[T]`, `img.dma_pool[T]`,
   `img.supervise`, `img.check_layout`, `decl.handle()`,
   `img.seal()`) is compiler-recognized by callee key — prelude-style
   declarations, no stdlib source needed. Intrinsics are legal only
   during an `@image` evaluation (a named diagnostic anywhere else,
   including `@test`s and const initializers); `eval::legal`'s
   exhaustive matches gain their first real illegal arm. Evaluation
   builds one plain `ImageGraph` struct (BTreeMaps + construction-order
   Vecs) — declarations recorded in program order, every argument a
   fully evaluated `Value`. The image's name and target come from
   `Image(...)` — comptime-checked source, nowhere else.

   Sub-notes (recorded at item B execution, 2026-07-23 — every typing
   choice the plan left open): the builder surface is **two opaque
   builtin resource types**, neither backed by a real declared struct —
   `Image` (the builder itself, and `img.seal()`'s own result: the same
   type serves both, matching 02 §12.1's own `-> Image` / `return
   img.seal()` shape) and `ImageDecl` (one shared type for *every*
   declaration handle — device, driver, actor, pool, dma pool, and
   `decl.handle()`'s own passthrough — since nothing before item C's
   graph checks needs to tell them apart structurally; `types::resolve_named`
   gains the one arm `Image` needs to resolve as a type annotation,
   `ImageDecl` needs none, since source never spells it). Every intrinsic
   call is one new typed node, `sema::typed::TypedExprKind::Intrinsic{key,
   receiver, type_arg, args}` (not folded into the ordinary `Call` node):
   none of these builder calls have a declared parameter list to align
   `args` against positionally or by stored default, so every argument
   keeps its own source label instead, and `type_arg` is the builder's own
   bare type-name slot (`device[D]`, `pool[T]`, `dma_pool[T]`'s bracket, or
   `driver`/`actor`'s leading unlabeled argument) resolved once, up front,
   as a real `Type`. `img.driver`/`img.actor`'s own leading type argument
   resolves through `mctx.structs` directly, not the ordinary type-
   annotation resolver (`ModuleCtx::resolve_type`/`mctx.shapes`) — the one
   deliberate divergence, since only `mctx.structs` (not `mctx.shapes`) is
   spliced from an imported module (item A's own disclosed scope line),
   so a driver/actor struct declared in another module resolves here in
   call/callee position exactly like constructing it would (golden/image-project
   exercises this directly). `img.pool`/`img.dma_pool`'s own `name=`
   argument is the one builder argument that is not an ordinary value
   expression — a bound `pool` name is otherwise only ever spelled inside
   `own[P] T` — so it is its own typed leaf, `TypedExprKind::PoolName`,
   recognized only in that one labeled position, never falling through to
   the ordinary name resolver (which would, correctly, reject a bare pool
   name anywhere else). Two prelude helpers 05 §9/02 §11 name but that
   ship as no stdlib source share the identical `Intrinsic` node kind for
   the dumbest possible reason (one dispatch point in `eval::interp`, no
   second mechanism) despite **not** being graph-building effects: `Target`/
   `Restart` are recognized as fixed prelude enums (`sema::prelude::builtin_enum_variants`,
   injected into every module's own `TypedProgram::enums` so the existing
   `Option`/`Result`-shaped evaluator machinery indexes them for free), and
   `RestartIntensity(max=..., within=...)`/`seconds(n)` are recognized call-
   by-name exactly like `Some`/`Ok`/`Err` — legal *anywhere* (`typed::is_restricted_intrinsic`
   deliberately excludes both), since neither mutates the build graph.
   `seconds(n)` evaluates to a plain nanosecond count (`Value::U64`);
   `RestartIntensity(...)` evaluates to a positional `Value::Tuple` (not
   `Value::Struct` — no `TypedStruct` backs it, so nothing ever field-
   accesses it, only records/renders it verbatim). The evaluator itself
   threads exactly one mutable slot for all of this: `eval::interp::Interp`
   gains `image: Option<ImageGraph>` (the sole active builder — decision 6
   guarantees at most one) and `sealed_image: Option<ImageGraph>` (`img.seal()`'s
   own stashed result, read back by the new top-level entry point
   `eval::interp::eval_image` once the `@image` fn's body finishes) —
   every `Image`-rooted intrinsic mutates `ctx.image` directly rather than
   threading a builder value through `env`; `decl.handle()` is the one
   intrinsic that reads its own `receiver` instead (there being no single
   global "the declaration" to default to).
6. **Exactly one reachable `@image` in the closure** (04 §1): zero or
   more than one is a named diagnostic listing every candidate.
   `wrela build` pointed at a file whose closure has no `@image` is an
   error, not a no-op.
7. **Graph checks are M4's "Closure" subset, each one named** (02
   §12.1, 05 §9): construction edges form a DAG (cycle printed in
   full, the wait-cycle diagnostic precedent); every `pool` name bound
   exactly once by `img.pool`/`img.dma_pool` and never constructed as a
   value; `img.driver`/`img.actor` arguments match the actor's `init`
   after generated capabilities and handles are substituted
   (`decl.handle()` produces `Actor[A]`); exactly one supervising
   parent per actor/driver (the image root is the implicit parent of
   top-level `supervise` groups — pin the doc's exact rule in goldens);
   a resource `init` argument without a recovery source is an error;
   `seal` succeeds only when every declaration is fully bound. What M4
   does **not** check is also named: mailbox capacity derivation
   (declared numbers recorded as-declared, M6), placement (M8), memory
   ceilings (M5).
8. **The report is one stable text artifact in the M1 dump style** —
   `Kind key=value` lines, two-space indent, fixed section order, a
   versioned header line (`ImageReport v0`), facts only: build identity
   (compiler revision, target, quota constants, input digests — every
   file in the closure), the image, devices, drivers/actors with their
   init wiring and declared mailboxes, every logical actor edge, pools
   with capacities and restart provisions, the supervision tree,
   registered (unrun) layout asserts. **No placeholders for facts that
   don't exist yet** — a section absent in M4 is absent, and later
   milestones append sections without reshuffling existing ones. The
   summary is a few fixed lines to stdout; the report is the artifact.
9. **Report determinism is an oracle from day one**: `xtask` builds
   every project-shaped golden twice (fresh output dirs) and
   byte-compares the reports — the M4 down-payment on 04 §8's
   `compiler.repro.byte-identical` (which stays a gap until the binary
   image exists, M5). Input digests use a single hardcoded hash
   (implemented in-tree; no new dependency).
10. **`img.check_layout` registers; nothing runs it.** There is no
    layout until M5, so a registered `@layout_assert` is recorded in
    the report and the build then **fails closed** naming M5 if any is
    registered — never "asserted against nothing". Same for
    `img.dma_pool`'s `@layout(dma)` requirement: `@layout` structs are
    not validated until the hardware milestone, so `dma_pool` fails
    closed naming it (gap `image.graph.dma-pools`).
11. **`wrela build <file.wr>`** writes `<image-name>.report.txt` next
    to the root file (or `--out-dir`), prints the summary, exits
    nonzero on any diagnostic. Golden cases for projects are
    directories with `src/` + a named root + `expected/report.txt`
    (+ `expected/build-err.txt` for rejection cases) — the golden
    runner learns this one new case shape.
12. **Code layout**: `crates/wrela-compiler/src/loader.rs` (root
    anchoring + import-closure walk), `sema/` grows the multi-module
    entry (collect-all then the existing pipeline), `eval/image.rs`
    (intrinsics + `ImageGraph` + graph checks), `report.rs`
    (rendering). Long obvious files, plain structs, BTreeMap everywhere
    output-touching.

The **group/scoped-pool unification** question is settled (human
decision, 2026-07): two constructs, deliberately — one region model,
two binding disciplines, stated normatively in 04 §3. M4's `img.pool`
goldens pin the two-construct surface with that decision on the record.

### A. The loader: root anchoring + import closure
`loader.rs`: module-path ↔ file-path agreement walked upward from the
root; transitive import closure in BTree order; `core` → `stdlib/`;
visited-set walk (import cycles legal, decision 3); the `build`
diagnostic category. Import resolution whole-program (decision 2);
`sema.names.imports` and `build.root-file-closure` flip. Goldens: a
multi-module accept project, an import-cycle accept project, loader
error cases (path disagreement, missing module file, missing name,
non-pub import, collision, core-miss).
Opens: `build.category.named-diagnostics`.

### B. `@image` evaluation
Decision 5: intrinsic recognition by callee key, `ImageGraph`
construction in program order, the `@image`-context legality carve-out
(intrinsics illegal elsewhere — `eval/legal.rs`'s first real illegal
arm, and `comptime.legality.inferred` finally earns golden evidence and
flips). `@image` bodies stop failing closed in sema (they are ordinary
comptime-legal code plus intrinsics). Opens:
`image.eval.builder-intrinsics`, `image.eval.comptime-context`; flips
`comptime.legality.inferred`.

Sub-note (recorded at item B execution, 2026-07-23): the item's own
required stable dump lands as a new CLI stage, `wrela dump --stage=image
<root.wr>` (`bin/wrela.rs::run_image_stage`) — forking single-file vs.
whole-closure exactly like `--stage=check` already does (`sema::check_typed`
vs. the loader + the new `sema::check_program_typed`, which mirrors
`check_program` but keeps every module's own checked `TypedProgram`
instead of discarding it), finding the one reachable `@image` fn across
every checked module (`TypedProgram::image_fn`) and evaluating it
(`eval::interp::eval_image`). Zero or more than one `@image` fn across
the whole closure is `error[build]: no \`@image\` fn found in the build
closure` / `error[build]: more than one \`@image\` fn reachable in the
build closure (...)` — this item's own minimal slice of decision 6; item
C grows the "list every candidate" diagnostic further. The dump itself
(`eval::image::dump`) is the M1 style: a versioned header (`ImageGraph
v0`), one section per declaration kind, absent entirely when empty — no
report-shaped placeholders this early. `eval/image.rs` is new
(`ImageGraph`/`DeclArg`/`ImageDeclRef` + the builder methods each
intrinsic calls + the dump + its own unit tests for graph-recording
order and `is_restricted_intrinsic`'s exact set); `eval/value.rs` gains
one variant (`Value::ImageDecl`); `eval/interp.rs` gains the `Intrinsic`
dispatch and `eval_image`; `eval/legal.rs`/`eval/mod.rs` gain the
legality carve-out (see decision 5's own sub-notes above for the typing
and legality-mechanism detail). `sema::access`/`sema::bodies` both grow
a small, explicit Image/ImageDecl recognition arm at their own method-
call dispatch points — necessary because both passes independently
re-derive a best-effort type for a method call's own receiver, and
neither can (nor should) discover a compiler-recognized pseudo-type from
`mctx.structs` the way it discovers a real declared struct.

## Non-goals (M5+ territory)

No manifest and no build configuration, permanently unless a
demonstrated need reopens the docs (02 §2.1); no code emission, layout,
linking, or `@layout_assert` execution (M5); no async/actor **body**
typing — `await`/`send`/`with` stay fail-closed, actor participation in
the image graph is by signature (M6 territory, and the reason the
example appliance's handlers are synchronous); no mailbox capacity
*derivation* from sender sets (M6 — declared capacities are recorded
verbatim); no placement inference (M8); no `@layout` struct validation
or DMA pools (hardware milestone — explicit gap); no package
acquisition or lockfile; no image-test scenario execution (scenario
files are an M5+ runner concern); no comptime caching (unchanged: needs
a profile the cleverness budget accepts); no report fields invented
ahead of the milestone that can prove them; no whole-tree "check
everything under src/" sweep (tooling, not this milestone).
